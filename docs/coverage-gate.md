# Гейт `coverage:changed`

Обязательный гейт **каждой** задачи (FAST и FULL-трек, см. [agentic-pipeline.md](./agentic-pipeline.md)):
`npm run coverage:changed` проверяет 100% покрытие ровно тех строк/веток, которые задача добавила или
изменила (industry-standard patch coverage), а не весь файл и не проект целиком. Реализация —
`scripts/patch-coverage.mjs` (тонкий оркестратор: git, спавны, ФС, печать) + чистые модули без I/O в
`scripts/patch-coverage/`:

- `branchFacts.mjs` — независимый от c8 детектор ветвлений в исходнике (TypeScript AST);
- `diffBase.mjs` — выбор базы сравнения патча и разбор добавленных строк;
- `verdict.mjs` — разбор `lcov.info`, канарейка достоверности данных о ветках, сам вердикт;
- `shards.mjs` — планирование порций прогона и сверка их отчётов.

Эта пара документ+модули существует потому, что гейт был **ложно-зелёным**: в старом прогоне из 263
файлов lcov-записи `BRDA:` (данные о ветках) были только у 85 — по остальным 178 гейт утверждал
«ветки покрыты», не имея о них ни одного факта, и заодно завышал покрытие строк (`LH == LF` при
плоских, не блочных данных). Ниже — что нужно знать, чтобы не наступить на то же и не чинить
инструмент вместо теста, когда вердикт выглядит непривычно.

## Как читать вердикт: три кода возврата

`scripts/patch-coverage.mjs` завершается одним из трёх кодов (формирует `verdict.mjs`):

- **0 — GREEN.** Все добавленные/изменённые строки покрыты, ветвления в затронутых строках либо
  отсутствуют, либо покрыты, канарейка деградации (см. ниже) не сработала.
- **1 — RED, покрытие реально неполное.** Есть непокрытая добавленная строка, либо в затронутом
  диапазоне ветвления есть запись `BRDA` со значением `taken ∈ {'-', '0'}` (ветвь не исполнена), либо
  файл вообще не загружался тестами. **Действие: допишите тест.** Это штатный «красный» TDD-цикла.
- **2 — RED, данным нельзя верить.** Причины: `c8` не сформировал `lcov.info`; после выбора базы диффа
  набор изменённых production-файлов пуст (почти всегда значит неверную базу, а не «нечего
  проверять» — см. `COVERAGE_ALLOW_EMPTY` ниже); в диапазоне ветвления детектор нашёл конструкцию, но
  **у файла в lcov нет вообще ни одной записи `BRDA`** (не только в этом диапазоне — во всём файле);
  доля таких файлов по всему прогону превысила порог канарейки. **Действие: перемерьте** (переисполните
  `coverage:changed`; если повторяется — см. разделы «Ограничение V8» и «Канарейка» ниже), а **не**
  дописывайте тест — тесту в буквальном смысле нечего закрывать, если измерение не состоялось.

**Не путать 1 и 2.** Отсутствие `BRDA` в диапазоне само по себе — это код 1 в подавляющем большинстве
случаев (замер: у `if`-диапазонов 495 промахов `BRDA` из 2696 — это штатное поведение V8, он не создаёт
отдельный блок для ветви, которая на прогоне всегда берётся одним и тем же образом; для второй,
непройденной ветви нужен тест). Различитель между 1 и 2 — **есть ли у файла хоть одна запись `BRDA`
где угодно**: если есть — измерение файла состоялось, и пустой диапазон значит «эта конкретная ветвь не
исполнена» (код 1, пишите тест на неё). Если у файла нет `BRDA` вовсе — измерение не состоялось
(код 2, перемерьте, тест писать не на что). Спутать эти два случая означает либо бесплодно гонять новые
прогоны там, где нужен тест, либо писать тест на то, что физически не в состоянии измериться.

## Ограничение V8 и зачем нужно дробление прогона

Корень прежней поломки — свойство самого процесса Node, а не какого-то теста. Замерено на сыром
`NODE_V8_COVERAGE` (поле `functions[].isBlockCoverage`): **полный прогон** (все тесты в одном
долгоживущем процессе `@vscode/test-electron`) — 615 инструментированных скриптов, из них **блочных
0**; тот же набор, разбитый на **короткие** прогоны — 1224 скрипта, из них блочных **1219**.
Долгоживущий процесс тестов теряет поблочную детализацию V8 целиком: без неё `v8-to-istanbul` не может
положить в `lcov` ни одной записи `BRDA`, и «100% по веткам» превращается в молчаливый ложный зелёный.

**Проверено и не работает — не пробовать заново:**

- `v8.setFlagsFromString('--no-flush-bytecode')` из кода теста в рантайме — не восстанавливает
  поблочную детализацию;
- `NODE_OPTIONS` в любом виде: `--max-old-space-size` не помогает, а `--no-flush-bytecode` Node
  отвергает как недопустимый флаг именно через `NODE_OPTIONS`;
- периодические вызовы `v8.takeCoverage()` по ходу прогона — детализация есть только в самом первом
  снимке, дальнейшие снимки её не возвращают;
- `--js-flags` у Electron — до процесса расширения (Extension Host) не доходит.

**Решение — дробление.** `scripts/patch-coverage.mjs` бьёт скомпилированные тестовые файлы на порции
(`planShards` в `shards.mjs`) и прогоняет каждую порцию в **свежем** процессе
`node ./out/test/runTests.js` с общим `NODE_V8_COVERAGE`, затем сливает профили всех порций одним
`npx c8 report`. Доля блочного покрытия внутри порции — 0.994–0.995 против нуля у цельного прогона;
доля файлов с `BRDA` выросла до 226 из 296.

Дефолт — **8 порций**, не 4 (`COVERAGE_SHARDS`, см. ниже). Причина замерена, а не выбрана произвольно:
один тяжёлый тест со сканом корпуса `example/` (`typedFieldOwnerRoleRules`) своим давлением на GC
обнуляет блочное покрытие **всей порции целиком**, в которую попал, — 40 тестовых файлов в одной
порции дали 0 блочных скриптов и 0 записей `BRDA` по всем 160 файлам `lcov`, включая соседние по
алфавиту (тестовый файл и его production-файл обычно соседствуют по имени). При порциях по ~20 файлов
эта катастрофа не воспроизводится (доля блочных 0.76–0.90). При 4 порциях гейт слеп к веткам целого
алфавитного среза проекта — отсюда дефолт 8.

Цена дробления — новый класс ошибки: «часть тестов молча не прогналась» (упавшая порция, пропущенный
или задублированный тестовый файл между порциями). Поэтому каждая порция обязана отчитаться
(`MOCHA_SHARD_REPORT`, пишет `src/test/suite/index.ts`), а `verifyShardReports` (`shards.mjs`) сверяет
отчёты между собой и с ожидаемым полным набором файлов **до** сборки итогового `lcov` — любое
рассогласование даёт код 2 (`RED — прогон шардов рассогласован, данным покрытия верить нельзя`), а не
частичный отчёт, неотличимый от валидного.

## Правило диапазонов ветвлений

`branchFacts.mjs` строит диапазоны строк по AST TypeScript (`typescript` compiler API), не по тексту —
строка, комментарий или regex-литерал не должны маскироваться под конструкцию. Ключевое и самое
хрупкое правило: **диапазон — это то место, куда `v8-to-istanbul` реально кладёт запись `BRDA`, а не
то, где конструкция начинается.**

- `if` / тернарник / логическая операция (`&&`, `||`, `??`) — диапазон это заголовок/условие, конец —
  конец выражения-условия (не всего оператора, иначе в зону проверки попало бы тело со всеми своими
  строками).
- `switch` — диапазон **НЕ** заголовок `switch (x)`, а **каждая `case`-клауза отдельным диапазоном**.
  Замерено на реальном `lcov.info` (295 файлов): диапазон-заголовок дал **1 попадание `BRDA` против 20
  промахов** (и то единственное попадание принадлежало соседней конструкции) — то есть любая правка
  строки `switch (x)` требовала данных, которых V8 в заголовок в принципе не кладёт: неисправимый
  красный, не закрываемый ни тестом, ни `c8 ignore`. После перехода диапазона на сами клаузы —
  **235 попаданий против 7**. `default` в диапазоны намеренно не включён — его поведение не замерено, а
  лишний диапазон без источника `BRDA` снова дал бы неисправимый ложный красный.

**Возвращать диапазон `switch` к заголовку нельзя.** Тело конструкции в диапазон не входит никогда —
телом ветвление не является, а его строки расширили бы зону проверки на посторонний код.

## Инвариант: детектор обязан недооценивать

Список распознаваемых конструкций в `branchFacts.mjs` — сознательно консервативный (`if`, тернарник,
`&&`/`||`/`??`, `case`-клаузы). Условный тип TypeScript (`T extends X ? A : B`) туда не входит, хотя
выглядит похоже на тернарник, — он не эмитится в JS вообще, и включение его в детектор дало бы
конструкцию, которую физически невозможно покрыть тестом.

Асимметрия цены ошибки: **пропущенное ветвление** — гейт просто промолчит про него (не хуже поведения
до переделки, когда о ветках вообще не было фактов). **Лишнее найденное ветвление** (конструкция,
которую детектор посчитал ветвлением, а V8/JS реально так не трактует) — вечный неисправимый красный:
закрыть тестом ветку, которой не существует в скомпилированном JS, невозможно в принципе. Поэтому при
любом расширении списка конструкций в `branchFacts.mjs` подтверждайте эмпирически (реальным
`lcov.info`, как в разделе выше про `switch`), что V8 действительно кладёт туда `BRDA`, — а не
добавляйте конструкцию «по аналогии» с уже поддержанными.

## Канарейка деградации

`summarizeBranchCoverage` (`verdict.mjs`) считает долю файлов, у которых детектор нашёл ветвления, но в
`lcov` по ним нет **ни одной** записи `BRDA` во всём файле (не только в затронутом диапазоне —
буквально нигде). Это прямой признак повторной потери поблочной детализации из раздела «Ограничение
V8» выше: на здоровом дроблёном прогоне доля мала и объясняется консервативностью детектора
(пропущенные им конструкции считаются в других файлах, но не создают ложных провалов здесь); резкий
рост означает, что дробление перестало помогать (порции слишком крупные, вернулась деградация процесса
и т.п.), и **всему вердикту по веткам для этого прогона верить нельзя**.

Порог — `COVERAGE_MAX_DEGRADED_SHARE` (переменная окружения `COVERAGE_MAX_DEGRADED`, дефолт `0.25`).
Превышение (строго больше порога, ровно на пороге — ещё норма) поднимает **код 2** независимо от
остальных результатов: `ДЕГРАДАЦИЯ ПОКРЫТИЯ: доля файлов с ветвлениями, но без единой записи BRDA —
<доля> при пороге <порог>`.

**Если канарейка сработала:** не переписывайте тесты и не увеличивайте порог как способ «починить»
код 2 — это маскировка симптома. Сначала увеличьте `COVERAGE_SHARDS` (больше, но более мелких порций
на прогон) и повторите; если не помогает — ищите новый «тяжёлый» тест, аналогичный
`typedFieldOwnerRoleRules` (давление на GC, большой корпус файлов), который своей порцией тянет вниз
соседей по алфавиту, и рассмотрите его изоляцию в отдельную порцию.

## Переменные окружения

| Переменная | Назначение | Дефолт |
|---|---|---|
| `COVERAGE_SHARDS` | число порций прогона (см. «Ограничение V8») | `8` |
| `COVERAGE_MAX_DEGRADED` | порог канарейки деградации (доля, 0..1) | `0.25` |
| `COVERAGE_BASE` | явная база диффа (`git ref`) вместо автоопределения | не задана |
| `COVERAGE_ALLOW_EMPTY` | `1` — осознанно подтвердить пустой патч (нет изменённых production-файлов) как валидный GREEN, а не как код 2 | не задана |

`COVERAGE_BASE` нужен, если автоопределение (`diffBase.mjs`) выбрало не ту точку расхождения — обычно
после ручных манипуляций с историей ветки; в норме автоопределение ищет точку расхождения с
`origin/develop`, затем `origin/main`, и включает в критерий как `modifiedAgainst`, так и `untracked`
файлы (задача, добавившая только новые файлы, иначе давала бы пустой `git diff --name-only` и молча
уезжала на следующий upstream, вменяя долг покрытия чужих коммитов).

**`MOCHA_SHARD_LIST` / `MOCHA_SHARD_REPORT` / `MOCHA_SHARD_INDEX` / `MOCHA_SHARD_TOTAL`** — внутренний
контракт между `scripts/patch-coverage.mjs` (оркестратор) и `src/test/suite/index.ts` (раннер): их
выставляет только сам гейт для передачи манифеста порции и получения отчёта о её выполнении. Вручную
их не задавать — обычный `npm test`/`test:fast` их не использует и прогоняет полный набор.

## Известное место без `BRDA`: `CommandInterfaceService.ts`

`src/infra/xml/CommandInterfaceService.ts` содержит `switch` с клаузами `'hide'`/`'show'`/`'place'`/
`'order'`/`'subsystem-order'`/`'group-order'` (строки диспетчера команд интерфейса). На части клауз V8
сливает соседние блоки в один (в частности `case 'hide': case 'show': { ... }` — общее тело для двух
меток), из-за чего часть исполненных клауз не получает собственной записи `BRDA`, хотя реально
покрыта. Если встретите этот файл (или структурно похожий `switch` с общими телами у соседних `case`)
с сообщением о непокрытых ветках при фактически пройденных тестах — это не пробел в тесте, а
особенность генерации байткода V8 для слитых блоков. Закрывается точечным `/* c8 ignore */` над
конкретной клаузой с обоснованием (см. правило 4 раздела «TDD и покрытие» `CLAUDE.md`), а не
попытками добавить ещё один тестовый сценарий на уже пройденный код.

## Особенность окружения: версия VS Code для тестов

В текущем окружении разработки дефолтная версия VS Code, которую `@vscode/test-electron` подтягивает
без явного указания, падает при прогоне тестов с `SIGKILL`. Рабочий прогон требует явного
`VSCODE_TEST_VERSION=1.129.1` (см. `CLAUDE.md`, раздел «Команды», про порядок чтения этой переменной в
`src/test/runTests.ts` до `sanitizeInheritedIdeEnv`). Это наблюдение конкретной машины/момента времени,
не требование проекта — на другом окружении дефолтная версия может быть рабочей; если `npm test` падает
без понятной причины ДО начала тестов, попробуйте зафиксировать версию явно, прежде чем разбираться
глубже.
